# Bridgev2 Progress

This document tracks the Beeper-facing `bridgev2` implementation that wraps the existing Snapchat Web sidecar.

## What exists now

The new `bridgev2` code lives in:

- `cmd/mautrix-snapchat-bridgev2/main.go`
- `pkg/connector/connector.go`
- `pkg/connector/login.go`
- `pkg/connector/api.go`
- `pkg/connector/ids.go`
- `pkg/connector/example-config.yaml`

## What this new bridgev2 path can do

### 1. Build as a real `mxmain` bridge binary

The new binary builds in WSL with:

```bash
go build -tags goolm ./cmd/mautrix-snapchat-bridgev2
```

This is important because it means the project is no longer only a custom HTTP wrapper. It now has a proper Beeper/Matrix bridge entrypoint.

### 2. Generate a real bridgev2 config

The binary supports:

```bash
./mautrix-snapchat-bridgev2 -e -c /tmp/mautrix-snapchat-bridgev2.yaml
```

That generated config already includes the Snapchat sidecar settings under `network:`.

### 3. Define a browser-session login flow

The login flow is intentionally based on the working Snapchat Web sidecar, not guessed private mobile endpoints.

Current model:

1. Bridge user selects the `browser-session` login flow.
2. Bridge tells the sidecar to start Snapchat Web login.
3. User completes authentication in the browser.
4. Bridge waits for the authenticated browser session and completes login metadata if authentication succeeds before timeout.

The login wait timeout is now configurable with `network.login_wait_seconds`.

### 4. Define a first network API layer

The current `SnapchatAPI` implementation can:

- treat the sidecar as the remote transport
- send Matrix text into Snapchat chats
- poll Snapchat chats and messages
- queue remote message events into bridgev2

This is the first real Beeper-facing slice of the project.

### 5. Persist chat routing state

The bridgev2 connector now stores the Snapchat chat mapping in SQLite so chat routing can survive restart more cleanly.

Current persistent state includes:

- `chatId -> chatName`
- preview text
- last message text
- unread state

That state lives in the bridgev2 state DB configured with `network.state_db_path`.

## What is still incomplete

### 1. Login UX is still rough

The bridgev2 login step still asks the user to type `START`. It now waits for browser auth automatically, but it is still functional scaffolding rather than polished UX.

### 2. Portal identity is still derived from scraped Snapchat Web data

Portal IDs now use stable chat IDs generated by the connector instead of raw display names, which is an improvement, but they are still derived from scraped Snapchat Web data rather than a first-party conversation ID.

### 3. Remote event handling is not production-clean yet

The poll loop exists, but message parsing and dedupe are still only as good as the current browser scraper. This means Matrix-side sync is still limited by the connector quality.

### 4. Matrix metadata is still minimal

Room names, avatars, membership lists, typing, receipts, and media handling all still need to be filled out properly.

## Why this is still meaningful progress

This is the point where the project stops being “a Snapchat Web automation service with a helper HTTP wrapper” and starts being “a Beeper-shaped bridge that uses Snapchat Web as its transport”.

That is the right transition to make before improving login UX, message fidelity, and final `bbctl` onboarding.

## Current WSL commands

Build and run:

```bash
~/Codex/scripts/run_bridgev2_wsl.sh -c /path/to/config.yaml
```

Important build note:

- use the `goolm` tag in environments without `libolm` headers

```bash
cd ~/Codex
go build -tags goolm -o ./bin/mautrix-snapchat-bridgev2 ./cmd/mautrix-snapchat-bridgev2
```

Generate example config:

```bash
cd ~/Codex
./bin/mautrix-snapchat-bridgev2 -e -c /tmp/mautrix-snapchat-bridgev2.yaml
```

Generate registration:

```bash
cd ~/Codex
./bin/mautrix-snapchat-bridgev2 -g -r /tmp/mautrix-snapchat-registration.yaml -c /path/to/config.yaml
```

The registration command requires a config with real homeserver values set.
